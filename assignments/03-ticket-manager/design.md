# Ticket Manager Design

## Architecture

The application uses four layers:

```text
CLI layer
    ↓
Application service layer
    ↓
Domain layer
    ↓
Repository/data layer
```

The CLI depends on the service. The service depends on the domain model and repository contract. The in-memory repository owns storage details.

## Main classes

### Ticket

Represents one ticket. It owns an identifier, title, description, and status. It validates required values and status membership at construction.

### TicketStatus

Defines the allowed ticket statuses as an enum: `Open`, `In Progress`, and `Resolved`.

### TicketRepository

Defines the repository contract for adding, getting, listing, updating, and deleting tickets.

### InMemoryTicketRepository

Implements the repository contract using an in-memory dictionary keyed by ticket ID. Results are returned in creation order for predictable output.

### TicketService

Coordinates business operations. It validates inputs, enforces status transitions, delegates storage operations, and raises domain exceptions.

### TicketCLI

Reads terminal input, calls the service, and formats results. It does not contain domain validation or persistence logic.

### TicketManagerApp

Creates the repository, service, and CLI and runs the application session.

## Data model

Each ticket contains:

- ticket_id: unique non-empty string generated by the service
- title: non-empty trimmed string
- description: non-empty trimmed string
- status: `Open`, `In Progress`, or `Resolved`

## Business rules

1. A new ticket starts as `Open`.
2. Titles and descriptions are trimmed before validation.
3. Ticket IDs are immutable.
4. Updating a `Resolved` ticket is rejected.
5. Status changes only move forward through the allowed workflow.
6. Repository operations fail explicitly rather than silently ignoring errors.

## Validation rules

- `TicketStatus` validates the status value.
- `Ticket` validates required title and description values.
- `TicketService` validates required IDs and search input.
- Invalid data raises `ValidationError` without changing storage.

## Error rules

- `ValidationError`: invalid ticket or status data
- `TicketNotFoundError`: requested ticket does not exist
- `RepositoryError`: storage operation cannot be completed
- CLI errors are displayed to the user and do not terminate the session

## CLI menu

```text
Ticket Manager

1. Create Ticket
2. List Tickets
3. View Ticket
4. Update Ticket
5. Change Status
6. Delete Ticket
7. Exit
```

The CLI returns to the main menu after each operation except exit. It does not directly modify repository state.

## OOP constraints

1. Each class has one clear responsibility.
2. The service accepts and returns domain objects rather than CLI values.
3. The repository is injectable for testability.
4. Domain code depends only on Python standard-library types.
5. CLI formatting remains outside reusable business behavior.

## Test strategy

- Unit tests verify domain validation and status transitions.
- Service tests verify create, list, view, update, status change, and delete behavior.
- CLI tests verify menu navigation, output, and error recovery.
- Tests use the real in-memory repository and service implementations.
